# 报关智能体子智能体调用架构深度研究与系统优化方案

**研究日期：** 2026-06-23  
**研究对象：** 当前报关智能体、Agent V1 中间层、OpenCode 子智能体调用链  
**结论级别：** 架构决策与实施建议，不替代后续压测和安全评审

## 摘要

本研究比较了 OpenAI Agents SDK、LangGraph/LangChain、Anthropic Claude Code、Google ADK、Microsoft AutoGen、CrewAI 与 A2A Protocol 的官方设计，并审计了本项目 `CustomsChatAgent`、`AgentRunService`、工具超时策略和 Agent V1 事件协议。结论是：本系统不宜采用多个智能体轮流直接接管用户会话的 Swarm，也不应继续把 OpenCode 作为一个嵌在 `chat_agent.py` 中的长耗时字符串工具。最适合当前产品边界的方案是“**单一对外主智能体 + 内部 Manager/agents-as-tools + 固定流程 LangGraph + 可选 A2A 适配器**”。

主智能体继续作为平台唯一入口，负责理解用户目标、选择能力、整合结果和最终答复；子智能体在独立上下文中完成边界清晰的任务，只返回结构化结果、证据和产物。固定报关流程、状态迁移、审单前置条件等确定性业务逻辑继续由 LangGraph/状态机控制，不交给子智能体自由决定。这样既保留系统现有的统一接口，也能获得上下文隔离、专业化、并行执行和团队独立维护的收益。

当前 OpenCode 调用已经具备“父智能体组织任务、独立会话、项目目录限制、产物路径校验、进程终止”的雏形，但仍存在五个关键问题：权限声明过宽、任务协议非结构化、直接调用分支绕过统一运行治理、240 秒内部超时与 3600 秒子智能体策略冲突、子智能体生命周期和产物没有进入 Agent V1 的标准事件/持久化体系。因此建议先做治理收口，再扩展新的子智能体类型。

## 1. 研究问题与方法

### 1.1 核心研究问题

1. 主流系统如何决定“何时调用子智能体、调用谁、传递什么上下文”？
2. 子智能体应当作为工具、handoff 目标、群聊成员，还是独立服务？
3. 如何限制权限、轮次、预算、并发和嵌套深度，避免失控？
4. 如何实现流式进度、取消、恢复、产物交付和父智能体验证？
5. 本系统应如何在尽量少改现有能力的前提下升级？

### 1.2 研究方法

本报告优先使用各框架官方文档、协议规范和官方工程复盘。纳入标准为：来源可验证、直接描述子智能体或多智能体调用机制、对上下文/权限/状态/可观测性至少一项有明确规则。营销性二手文章和无法验证的案例未纳入结论。项目审计基于当前仓库源码，重点检查 `src/services/chat_agent.py`、`src/services/tool_execution_policy.py`、`src/agent_api/events.py` 和 `src/agent_api/service.py`。

## 2. 主流子智能体调用模式

### 2.1 Manager / Agents-as-Tools：主智能体集中控制

在 Manager 模式中，子智能体以工具形式暴露，主智能体保持用户会话控制权。OpenAI Agents SDK 将“manager（agents as tools）”与 handoff 明确区分；LangChain 的 subagents 模式同样由主智能体路由，子智能体通常是无状态、独立上下文的调用，结果返回主智能体再综合。[R1][R5][R6]

这种模式的优势是：

- 用户始终面对同一个智能体，产品人格和责任边界稳定；
- 子智能体看不到不必要的完整历史，减少上下文污染；
- 父智能体可以验证、裁剪或拒绝子智能体结果；
- 不同团队可以独立开发子智能体，只需遵守统一任务/结果协议；
- 可以并行调用多个相互独立的专家。

代价是每次结果必须返回父智能体，多一次模型调用和汇总开销。LangChain 的官方对比指出，subagents 在单任务场景会比 handoff 多一次调用，但在多领域并行任务中通过上下文隔离减少总 token；其子智能体通常每次从新上下文启动。[R5]

**适合本系统：** 是。报关平台只需要暴露一个智能体，且父智能体必须对最终答复、风险提示和文件结果负责。

### 2.2 Handoff：转移当前会话控制权

OpenAI 的 handoff 被实现为模型可调用的转移工具，目标智能体接管后通常获得已有会话历史；可通过 `input_filter`、嵌套历史摘要或 history mapper 改变其可见上下文。官方文档还强调：模型生成的小段 handoff 元数据应与应用状态分离，现有用户/权限/依赖应放在运行时上下文中。[R2]

LangGraph 的 handoff 更明确地依赖持久状态，例如 `active_agent` 或 `current_step`。工具更新状态并路由到新节点；如果 handoff 工具写入消息，必须同时保留发起 tool call 的 AIMessage 与配对的 ToolMessage，否则消息历史不完整。[R7]

**适合本系统：** 仅适合未来需要专家直接持续追问用户的场景，例如“补件专员连续收集材料”。当前 OpenCode、法规研究、报告生成和审单不需要接管用户身份，因此不应采用 handoff。

### 2.3 Router / Custom Workflow：程序先决定边界

LangChain 把 Router 用于输入分类和并行分发，把 Custom Workflow 用于混合确定性逻辑与 agentic 节点；Google ADK 同样同时提供图工作流、动态工作流、协作代理与顺序/循环/并行模板，强调流程结构带来的可预测性、可靠性和上下文限制。[R5][R9]

**适合本系统：** 强烈适合报关流程。申报、受理、审单、补件、核税、放行等阶段有法定顺序和状态约束，应该由程序图控制；智能体负责某个节点内的判断或材料生成，而不是决定是否跳过业务前置条件。

### 2.4 Swarm / Group Chat：去中心化轮流协作

AutoGen Swarm 让智能体通过 handoff 消息决定下一位发言者，所有成员共享消息上下文；SelectorGroupChat 则由模型根据参与者描述和共享历史选择下一位发言者，并依赖终止条件结束循环。[R10][R11]

共享上下文有利于协作，但也会放大 token、上下文污染、循环和错误传播风险。AutoGen 特别提醒：并行 tool calling 可能同时生成多个 handoff，产生意外行为，因此示例中建议关闭并行 handoff。[R10]

**适合本系统：** 不作为主架构。报关是高约束业务，不能让多个智能体自由轮流决定流程。可在离线研究、方案评审等低风险任务中有限使用，但必须有 Manager、终止条件和预算上限。

### 2.5 跨服务 Agent-to-Agent

A2A Protocol 面向相互独立、内部实现不透明的智能体服务，提供能力发现、任务、上下文标识、流式更新、取消、消息、文件/结构化产物和认证授权。其原则是通过声明能力协作，而不暴露对方内部状态、记忆或工具。[R14]

**适合本系统：** 作为未来扩展边界，而非当前内部实现。当前所有能力部署在同一服务内，先使用内部 registry/adapter；当海关模拟、图像智能体或平台智能体独立部署时，再增加 A2A adapter，不必现在重写 Agent V1。

## 3. 业界规则设计的共同结论

### 3.1 子智能体必须显式注册

Claude Code 使用名称、description、system prompt、tools、disallowedTools、model、permissionMode、MCP servers、hooks、maxTurns、skills、memory 和 isolation 等字段描述子智能体；描述是父智能体判断何时委派的主要依据。[R4] LangChain 也把名称和 description 视为路由的核心提示，并建议少量静态智能体直接枚举，数量较大时再采用发现工具。[R6]

因此，不能只给主智能体一个模糊的“调用子智能体”工具。每个子智能体至少需要：稳定 ID、能力描述、适用/禁用场景、输入输出 schema、允许工具、权限模式、模型、超时、最大轮次、并发限制、是否允许写操作、是否允许再委派。

### 3.2 上下文工程比“多放信息”更重要

LangChain 把多智能体的中心问题定义为 context engineering，即决定每个 agent 看什么；其官方文档将上下文分为模型上下文、工具上下文和生命周期上下文，并区分瞬时与持久信息。[R5][R8] Claude Code 子智能体使用独立上下文窗口，返回摘要以避免把搜索结果、日志和文件内容灌入主对话。[R4]

Anthropic 的多智能体研究系统采用 orchestrator-worker：主代理制定策略，子代理在各自上下文并行探索，最后压缩关键结果返回。其复盘强调任务描述应包含目标、输出格式、工具/来源指引和边界，否则子代理会重复工作或遗漏范围。[R12]

因此，父智能体传给子智能体的不应是完整聊天历史，而应是结构化 `ContextPacket`：用户目标、当前任务、必要业务事实、允许使用的数据引用、交付格式、验收标准和权限。禁止传递 API Key、无关用户历史、内部 chain-of-thought 或整个工具目录。

### 3.3 最小权限必须由运行时强制，而非只写在提示词里

Claude Code 支持独立 tools/disallowedTools、permissionMode、MCP scope 和 isolation，说明权限是 agent 配置的一部分，而不是一句“请不要访问”。[R4] A2A 把认证、授权和任务内授权列为协议组成部分。[R14] OWASP Agentic Security Initiative 则将代理自治带来的权限滥用、身份和通信风险作为独立威胁面。[R15]

本系统应同时使用：

- Prompt 边界：告诉子智能体角色与禁区；
- Schema 边界：只允许声明的参数；
- Tool 边界：只注入需要的工具；
- Filesystem 边界：工作目录 allowlist/隔离目录；
- Action 边界：写入、执行、外发分别授权；
- Runtime 边界：超时、最大轮次、最大并发和预算；
- Human gate：危险写操作或外部提交需要审批。

### 3.4 生命周期必须可观测、可取消、可恢复

OpenAI Agents SDK 默认 trace 覆盖 LLM 生成、工具调用、handoff、guardrail 和自定义事件，并使用 trace/span 表达父子关系和起止时间。[R3] CrewAI 暴露 step/task callback、token usage、日志与 checkpoint，使长任务可以在完成关键任务后恢复。[R13] A2A 原生定义异步任务、SSE/推送更新、取消和 artifact 更新。[R14]

因此，子智能体不能只返回一个字符串。必须拥有独立的 `subagent_run_id`、父 `run_id`、状态机、事件序号、开始/结束时间、token/工具预算、错误码、产物列表和取消状态。

### 3.5 资源规模应与任务复杂度匹配

Anthropic 报告其多智能体研究系统在适合广度并行的内部评测上优于单代理，但多智能体 token 消耗约为普通聊天的 15 倍；其工程提示明确为简单事实、比较任务和复杂研究设置不同子代理数量与工具调用预算。[R12] 这表明“更多子智能体”不是默认更好，而是高价值、可并行、超长上下文任务的资源换性能策略。

本系统默认规则应是：能用普通工具解决就不派子智能体；能用一个子智能体解决就不并行；只有子任务独立且收益明确时才并发。

## 4. 当前系统子智能体实现审计

### 4.1 已具备的能力

当前 `delegate_to_opencode` 已做到：

1. 父智能体构造背景 prompt 和当前任务 prompt；
2. 为每次调用创建独立 OpenCode session；
3. 将操作范围文字限制在当前项目；
4. 对返回的 `OPENCODE_ARTIFACT_PATH` 做 `data/` 路径和文件存在性检查；
5. Windows 下使用 `taskkill /T /F` 终止子进程树；
6. 在工具策略中把 OpenCode 标记为 L5/SUBAGENT；
7. Agent V1 已具备 run、SSE、heartbeat、取消、输出文件和结构化错误的基础设施。

这些能力证明系统已经能“调用一个子执行器”，但还没有形成通用子智能体平台。

### 4.2 关键缺口

| 优先级 | 缺口 | 当前表现 | 影响 |
|---|---|---|---|
| P0 | 权限只靠提示词收敛 | OpenCode session 对 `edit`、`bash` 使用 `pattern=*` allow | 子智能体获得的运行时权限大于任务所需权限 |
| P0 | 两套执行路径 | 显式 OpenCode 文本触发后直接调用 `_delegate_to_opencode_tool`；正常工具调用走 LangGraph wrapper | 直接路径绕过统一工具包装、事件和策略 |
| P0 | 超时冲突 | HTTP 调用硬编码 240 秒；工具策略声明 L5 3600 秒 | 实际执行可能在 240 秒提前终止，配置名存实亡 |
| P0 | 取消不完全统一 | 父 run 可取消，但 OpenCode session 没有独立持久状态和 cancel endpoint | 难以准确区分用户取消、网络中断和子进程失败 |
| P1 | 无通用注册表 | 子智能体定义嵌在 `chat_agent.py` | 无法低风险增加审单专家、法规研究、报告专家等子智能体 |
| P1 | 输入非结构化 | 参数主要是 task 字符串，JSON 只可选 model/agent | 缺少目标、边界、验收标准、预算、上下文引用 |
| P1 | 输出非结构化 | 返回文本拼接 sessionID，产物依赖正则提取一行路径 | 无法稳定展示多产物、警告、指标和部分成功 |
| P1 | 上下文持久化不足 | `_opencode_context_by_session` 是进程内字典 | 重启丢失，无法跨实例恢复，也没有版本冲突检查 |
| P1 | 事件粒度不足 | 平台只看到一个普通 `tool_started/tool_finished` | 看不到子智能体阶段、内部工具、产物、等待和失败恢复 |
| P2 | 验证范围有限 | 只校验路径在 `data/` 且文件存在，文本最多读取 4000 字符 | 不校验 checksum、MIME、任务验收条件和代码测试结果 |
| P2 | 根目录依赖 cwd | 使用 `os.getcwd()` 决定 project root | 服务从不同目录启动时可能指向错误工作区 |
| P2 | 无成本与深度预算 | 无 maxTurns、maxChildren、token/tool-call 预算 | 复杂任务可能长时间或重复执行 |

### 4.3 对当前效果的判断

当前实现适合演示“主智能体能调用 OpenCode 并验证一个文件”，不适合宣称已经具备生产级子智能体编排。最大风险不在模型能力，而在缺少统一运行契约和运行时权限边界。继续追加更多硬编码子智能体工具会扩大 `chat_agent.py`、重复超时/取消逻辑，并让平台事件难以统一。

## 5. 推荐目标架构

### 5.1 总体原则

1. **对外仍只有一个 Agent V1 智能体。** 平台不感知内部有多少子智能体。
2. **内部默认采用 Manager/agents-as-tools。** 子智能体不直接接管用户会话。
3. **固定业务流程继续用 LangGraph。** 子智能体只能执行节点任务，不能跳过状态机。
4. **跨服务才使用 A2A。** 同进程内部先走 registry + adapter，避免过度设计。
5. **权限、预算和终止由程序控制。** 提示词只提供语义引导，不承担安全边界。

### 5.2 逻辑架构

```text
平台 / 用户
    |
Agent V1 Run API + SSE
    |
主报关智能体（Manager，唯一对外角色）
    |
DelegationPolicyEngine
    |-- 普通工具 / Skill / MCP
    |-- 固定报关 LangGraph 工作流
    `-- SubagentRunService
           |-- SubagentRegistry
           |-- ContextPacketBuilder
           |-- Permission/Budget Guard
           |-- EventBridge + RunStore
           |-- ArtifactGateway
           `-- Adapters
                 |-- OpenCodeAdapter
                 |-- ResearchAgentAdapter
                 |-- CustomsExpertAdapter
                 `-- A2AAdapter（未来）
```

### 5.3 子智能体注册模型

建议新增 `SubagentDescriptor`：

```json
{
  "agent_id": "opencode_builder",
  "version": "1.0.0",
  "display_name": "OpenCode 工程子智能体",
  "description": "处理当前仓库内的代码、脚本和文件任务",
  "use_when": ["代码修改", "仓库分析", "脚本执行"],
  "do_not_use_when": ["普通报关咨询", "直接提交真实海关"],
  "input_schema": "SubagentTaskRequest/v1",
  "output_schema": "SubagentResult/v1",
  "adapter": "opencode_local",
  "model_policy": "inherit_or_configured",
  "permission_profile": "project_write",
  "timeout_level": "L5",
  "max_turns": 30,
  "max_children": 0,
  "supports_stream": true,
  "supports_resume": false
}
```

默认 `max_children=0`，即子智能体不能继续生成子智能体。只有研究型编排器经显式配置后允许深度 2，避免递归失控。

### 5.4 结构化任务协议

```json
{
  "task_id": "subtask-uuid",
  "parent_run_id": "run-uuid",
  "parent_task_id": null,
  "agent_id": "opencode_builder",
  "objective": "修复指定模块并运行回归测试",
  "instructions": ["只修改当前项目", "保留用户已有改动"],
  "acceptance_criteria": ["目标测试通过", "返回修改文件清单"],
  "context": {
    "summary": "当前问题摘要",
    "business_case_id": null,
    "file_refs": ["src/example.py"],
    "artifact_refs": []
  },
  "permissions": {
    "filesystem": ["read:project", "write:project/src", "write:data/opencode_outputs"],
    "shell": ["python", "pytest", "git diff", "git status"],
    "network": false,
    "external_side_effects": false
  },
  "budget": {
    "timeout_seconds": 3600,
    "max_turns": 30,
    "max_tool_calls": 80,
    "max_output_chars": 20000
  },
  "idempotency_key": "parent-run + normalized-task-hash"
}
```

`context` 只放完成任务需要的事实和引用，不传完整会话。密钥、数据库连接和当前用户权限由 runtime context 注入，不由模型生成。

### 5.5 结构化结果协议

```json
{
  "task_id": "subtask-uuid",
  "status": "completed",
  "summary": "完成内容及关键结论",
  "findings": [],
  "artifacts": [
    {
      "kind": "document",
      "name": "result.md",
      "path": "data/opencode_outputs/result.md",
      "sha256": "...",
      "mime_type": "text/markdown"
    }
  ],
  "validation": {
    "criteria": [{"criterion": "目标测试通过", "status": "passed", "evidence": "pytest ..."}]
  },
  "warnings": [],
  "metrics": {
    "duration_ms": 0,
    "turns": 0,
    "tool_calls": 0
  }
}
```

父智能体只使用结构化结果中的 `summary/findings/artifacts/validation`，原始长日志保存到运行记录，不直接塞回主会话。

### 5.6 Agent V1 子智能体事件

建议在现有 SSE 中新增：

- `subagent_started`：agent_id、task_id、display_name、预算；
- `subagent_progress`：phase、message、progress_percent；
- `subagent_tool_started` / `subagent_tool_finished`：内部工具简要轨迹；
- `subagent_artifact_created`：统一映射到 `output_created`；
- `subagent_waiting`：等待用户、审批或外部依赖；
- `subagent_completed` / `subagent_failed` / `subagent_cancelled`；
- 所有事件带 `parent_run_id`、`subagent_run_id`、`sequence`、`timestamp`。

平台最低实现只需显示一行“正在调用某子智能体”和最终结果；高级平台可展开子事件。这样兼容当前前端，又不给平台强加复杂 UI。

## 6. 调用与治理规则

### 6.1 委派判定

按照以下顺序判定：

1. 固定 API/工具能直接完成：不委派；
2. Skill 能通过确定性脚本完成：调用 Skill；
3. 固定报关流程：进入 LangGraph workflow；
4. 任务需要独立长上下文、多步探索、代码执行或专业模型：委派子智能体；
5. 多个子任务相互独立且预期收益高：允许并行；
6. 任务强依赖共享上下文或顺序状态：禁止并行，使用 workflow 或单个子智能体。

### 6.2 默认资源限制

| 类型 | 并发 | 最大深度 | 最大轮次 | 默认超时 | 说明 |
|---|---:|---:|---:|---:|---|
| OpenCode 工程任务 | 1 | 1 | 30 | 3600 秒 | 写操作串行，避免仓库冲突 |
| 法规/资料研究 | 3 | 1 | 20/子任务 | 1200 秒 | 只读，可并行 |
| 审单专家判断 | 1 | 1 | 10 | 300 秒 | 输出结构化风险项 |
| 海关模拟智能体 | 1 | 1 | 状态图控制 | 120 秒/阶段 | 保持现有 workflow |
| 报告生成 | 1 | 1 | 20 | 1200 秒 | 产物走 OutputManager |

### 6.3 权限策略

- `read_only`：法规研究、代码审查、材料核验；
- `project_write`：仅允许项目内指定目录写入；
- `artifact_write`：只能写 `data/...outputs/`；
- `business_state_write`：只能通过封装后的业务工具修改案件；
- `external_action`：真实提交、邮件、平台上传等必须显式授权并记录审批。

禁止把 `bash=*`、`edit=*` 作为普通默认权限。OpenCode 若确需命令执行，应使用命令 allowlist 或隔离工作区，并对删除、Git 推送、网络上传等动作设置审批。

### 6.4 失败与恢复

1. 每次委派使用 idempotency key，重试不得重复创建文件或案件；
2. 父 run 取消必须级联取消所有 active child runs；
3. 工具超时与子智能体超时分开记录；
4. 子智能体失败返回结构化错误，父智能体可以降级为普通工具或向用户说明；
5. 长任务按阶段 checkpoint，服务重启后从最近完成阶段恢复；
6. 部分成功允许返回已生成产物和 warnings，不把全部成果丢弃；
7. 超过最大轮次、最大调用数或无进展阈值时自动终止。

### 6.5 父智能体验证

父智能体不能直接相信子智能体自述“已经完成”。验证至少包括：

- schema 校验；
- 产物路径、MIME、大小、SHA-256；
- 路径必须落在任务授权目录；
- 验收条件逐项给出证据；
- 代码任务至少检查测试命令/结果；
- 报关判断必须附规则、证据或 Mock 回执；
- 失败和降级必须向用户可见，禁止把 fallback 伪装成真实模型判断。

## 7. 分阶段优化计划

### Phase 0：现有 OpenCode 调用硬化（1—2 个工作日）

1. 删除 `_should_delegate_to_opencode` 的旁路执行，统一通过 LangGraph 工具或 SubagentRunService；
2. 把 240 秒硬编码超时改为 L5 策略配置；
3. project root 改用 `settings.BASE_DIR`/解析后的仓库根目录；
4. session 权限从 `edit=*、bash=*` 改为权限 profile；
5. 产物限制到单次 run 工作目录，并增加 checksum/MIME；
6. Agent V1 取消级联终止 OpenCode server/session；
7. 增加真实取消、超时、非法路径和重复调用测试。

**验收：** 同一 OpenCode 请求无论从网页还是 Agent V1 进入，都经过同一策略、同一事件和同一取消链。

### Phase 1：通用 Registry 与协议（3—5 个工作日）

新增独立 `src/subagents/` 模块，包含 `models.py`、`registry.py`、`policy.py`、`service.py`、`events.py` 和 `adapters/opencode.py`。把 OpenCode 内嵌代码迁出 `chat_agent.py`，主智能体只保留一个 `delegate_task` 工具。

**验收：** 新增子智能体只需要注册 descriptor 和 adapter，不修改主系统提示词主体或 Agent V1 路由。

### Phase 2：持久化、事件和恢复（3—5 个工作日）

1. 增加 `subagent_runs`、`subagent_events`、`subagent_artifacts` 持久化；
2. 建立 parent-child trace；
3. Agent V1 输出子智能体 SSE；
4. 支持取消级联、超时、部分完成和 checkpoint；
5. 平台仍可忽略子事件，只消费现有顶层事件。

**验收：** 服务重启后可查询子任务状态；取消父任务后不存在继续运行的子进程。

### Phase 3：增加专业子智能体（5—8 个工作日）

建议按风险从低到高增加：

1. `regulation_researcher`：只读法规/RAG/网络资料；
2. `document_reviewer`：读取结构化单证，输出差异和缺失项；
3. `report_writer`：消费已有审单结果，生成报告产物；
4. `customs_expert`：只在指定 LangGraph 节点内给出结构化建议；
5. 保留 `opencode_builder` 作为开发演示能力，不把它当报关生产能力。

**验收：** 每个 agent 有独立 schema、权限和评测集；没有 agent 能直接越过业务工具修改报关状态。

### Phase 4：评测与运行治理（持续）

建立至少 30 个代表性任务的评测集，指标包括：路由正确率、任务完成率、验收条件通过率、工具效率、平均时延、token 成本、取消成功率、越权率、产物有效率和父智能体验证拦截率。自由路径不要求固定步骤一致，重点评价结果与合理过程，这与 Anthropic 的多智能体评测经验一致。[R12]

## 8. 不建议采用的方案

1. **给每个现有工具都包装一个智能体。** 这只会增加模型调用和不确定性；确定性工具保持工具即可。
2. **把全部工具一次性交给每个子智能体。** “对主智能体暴露全部能力”不等于“每个子智能体拥有全部权限”。主智能体可见全集，子智能体按任务获得子集。
3. **让多个报关智能体共享完整聊天历史自由群聊。** 容易形成循环、重复判断和责任不清。
4. **只靠系统提示词限制文件和命令。** 安全边界必须由运行时权限、目录和审批强制。
5. **平台直接调用内部子智能体。** 当前平台契约应保持单一 Agent V1；内部实现可替换。
6. **一次性重写为某个新框架。** 现有 Agent V1、LangGraph、SSE、取消和 OutputManager 已经可复用，应先抽象服务层，而非框架迁移。

## 9. 最终建议

本系统下一步最有价值的工作不是增加更多“会调用模型的角色”，而是把现有 OpenCode 调用升级为一个可注册、可治理、可观察、可取消、可验证的子智能体运行时。完成 Phase 0 和 Phase 1 后，系统才真正具备扩展多个子智能体的基础。

推荐最终形态：

- 平台侧：始终只看到一个报关智能体和统一 Agent V1 协议；
- 主智能体：拥有全部能力目录，但根据用户目标进行最小委派；
- 子智能体：独立上下文、最小工具集、结构化任务、结构化结果；
- 固定业务：LangGraph/状态机保证顺序和规则；
- 外部独立智能体：未来通过 A2A adapter 接入；
- 全链路：统一 run/event/artifact/timeout/cancel/trace。

这条路线对现有代码改动可控，也能避免再出现“子智能体卡住、看不到过程、停止无效、权限过大、结果无法证明”等问题。
